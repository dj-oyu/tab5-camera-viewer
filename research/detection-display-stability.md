# Detection表示の安定性問題

## 現状の問題

### 1. SSE遅延問題 (解決済み - mainにマージ済み)
- **症状**: 検出表示に著しい遅延がある
- **原因**:
  - `parseDetectionJson()`内のデバッグログ（3箇所）がSerial出力でブロッキング
  - TCPバッファにSSEイベントが蓄積
- **解決策**:
  - デバッグログ削除
  - TCPバッファ内の全イベントを読み、最後の`data:`行のみ処理

### 2. 表示の不安定性問題 (未解決)

#### 2.1 症状
検出結果が素早く変化すると、UI上の表記が追い付かず「変な感じ」になる

#### 2.2 根本原因
**検出結果は本質的に不安定**

MLモデルの検出結果はフレームごとに変動する:
- 同じオブジェクトでも信頼度が変動（例: 0.65 → 0.67 → 0.64）
- 検出が断続的（フレームAで検出、フレームBで未検出、フレームCで再検出）
- 複数オブジェクトの検出順序が変わる
- 異なるラベルが交互に検出される（cupとdining_tableが交互に出る等）

#### 2.3 具体的なケース

**ケース1: 信頼度の変動**
```
time 0: cup (0.67)
time 1: cup (0.65)
time 2: cup (0.68)
→ メーターバーが細かく変動し、視覚的にノイズになる
```

**ケース2: 断続的な検出**
```
time 0: A検出
time 1: 検出なし
time 2: A検出
→ UIがA→空→Aと切り替わり、ちらつく
```

**ケース3: 複数ラベルの断続検出**
```
time 0: class_name A
time 1: class_name B
time 2: class_name A, class_name B
→ 表示が A→B→A,B と変わり、不安定に見える
```

**ケース4: 同ラベル複数オブジェクト**
```
time 0: person, person（2人検出）
→ ラベルベースの追跡では区別できない
```

## 検討した解決策

### A. レート制限（更新頻度制限）
- 表示更新を100-200ms間隔に制限
- **メリット**: シンプル
- **デメリット**: 本当の変化（新オブジェクト出現）も遅延する

### B. 時間ベースの安定化（連続一致）
- 同じ検出パターンがN回連続した時のみ表示更新
- **メリット**: ノイズ除去
- **デメリット**: 断続的な検出で永遠に更新されない

### C. ラベル独立追跡
- 各ラベルごとに最終検出時刻を管理
- 一定時間（500ms）検出されないラベルのみ消す
- **メリット**: 断続的な検出でも安定
- **デメリット**: 同ラベル複数オブジェクトに対応不可

### D. bbox位置ベース追跡
- ラベル + bbox位置で同一オブジェクトを識別
- IOU（重なり率）で追跡
- **メリット**: 最も正確
- **デメリット**: Detection構造体の拡張が必要、実装が複雑

### E. 追跡なし + レート制限
- 追跡をやめ、最新データをそのまま表示
- レート制限のみで安定化
- **メリット**: シンプル、同ラベル複数対応
- **デメリット**: 根本的な不安定さは残る
